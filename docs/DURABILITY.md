# Гарантии durability v0.1.0

Этот документ является нормативным описанием того, что означает успешный возврат операции записи.

## Sync

Порядок выполнения:

```text
полная проверка batch
→ preflight memtable
→ encode одного WAL-кадра
→ write_all кадра
→ sync_all WAL-файла
→ атомарное применение batch к memtable
→ возврат успеха
```

После успешного `Sync` запись должна восстанавливаться после аварийного завершения процесса при условии, что ОС
и файловая система честно выполнили успешный `sync_all`. Это проверяется отдельным process-abort тестом.

`Sync` не может абсолютным образом гарантировать сохранность при отключении питания на любом оборудовании. Реальный
результат зависит от файловой системы, mount options, накопителя, firmware, контроллера и наличия защищённого write cache.

## NoSync

Порядок выполнения:

```text
полная проверка batch
→ preflight memtable
→ encode одного WAL-кадра
→ write_all кадра
→ атомарное применение batch к memtable
→ возврат успеха
```

Перед возвратом не выполняется обязательный `sync_all`. Операция может пережить process crash благодаря page cache,
но ForgeDB этого не гарантирует. При падении ОС или потере питания подтверждённая запись может быть потеряна.

## DisableWal

Порядок выполнения:

```text
полная проверка batch
→ preflight memtable
→ атомарное применение batch к memtable
→ возврат успеха
```

WAL не изменяется. Запись существует только в памяти процесса и не восстанавливается после повторного открытия.
Этот режим предназначен для данных, которые caller способен полностью пересоздать.

## Database::close

`close()`:

1. помечает объект закрытым для новых операций;
2. синхронизирует оставшийся WAL writer;
3. закрывает writer;
4. освобождает системную блокировку `LOCK`.

Повторный `close()` идемпотентен. После закрытия методы чтения и записи возвращают `Closed`.

## Создание новой базы

Создание `IDENTITY` и нового WAL использует:

```text
create new file
→ write complete contents
→ file sync
→ close handle
→ directory sync
```

Directory sync реализован отдельно для Unix и Windows. Успех операции всё равно ограничен гарантиями платформы.

## Trailing partial frame

Если crash произошёл во время append, последний кадр может быть физически неполным. Recovery игнорирует только такой
последний кадр. При read-write открытии хвост усекается до последней полностью проверенной границы и синхронизируется.

Checksum mismatch полного кадра не считается допустимым хвостом и блокирует открытие.

## Таблица гарантий

| Режим | Видимость после успеха | Process crash | OS crash / power loss |
|---|---|---|---|
| `Sync` | Да | Должен восстановиться после успешного sync | Зависит от ОС, ФС и оборудования |
| `NoSync` | Да | Не гарантируется | Не гарантируется |
| `DisableWal` | Да, только текущему процессу | Теряется | Теряется |

## Что пока не покрывается

- durability SSTable и MANIFEST;
- атомарная публикация flush;
- WAL rotation;
- group commit;
- multi-file recovery;
- резервное копирование и restore;
- защита от silent corruption вне WAL.
