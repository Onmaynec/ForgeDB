# Переход ForgeDB v0.9.x → v1.0.0

## Поддерживаемый путь

Для **пользовательских persisted данных** переход с v0.9.0 на v1.0.0 не требует изменения WAL/SSTable/MANIFEST/CURRENT/IDENTITY/CF_REGISTRY на диске. Новая версия использует прежние WAL V1, SSTable V1, MANIFEST V1 reader/V2 writer, CURRENT V1, IDENTITY V1 и CF_REGISTRY V1. Новый LOGICAL_ARCHIVE V1 — самостоятельный формат переносимых логических данных; engine не начинает автоматически создавать такие файлы при normal open.

Перед обновлением остановите записывающие процессы, сделайте offline-копию каталога закрытой базы либо проверенный логический export и запустите `forgedb verify <database> --deep` и `forgedb inspect recovery-plan <database>`. Для нескольких Column Families согласованный экспорт между families требует остановить writes приложения: каждая family сохраняет собственный WAL и snapshot.

## Обновление приложения

1. Переключите зависимость Rust-кода на Git tag v1.0.0. Имя `forgedb` в публичном crates.io занято **другим** проектом, поэтому этот репозиторий нельзя получить обычной зависимостью без Git/path:
   ```toml
   [dependencies]
   forgedb = { git = "https://github.com/Onmaynec/ForgeDB.git", tag = "v1.0.0" }
   ```
2. Используйте Rust **1.89+** и проверьте `cargo test` на своей платформе.
3. Обновите CLI Windows/Linux на соответствующий portable бинарник и проверьте SHA-256 из Assets GitHub Stable Release.
4. Перезапустите приложение, затем выполните `forgedb doctor <database> --deep` для каждой важной базы.
5. Для постоянного резервирования используйте `forgedb export` и тестовый `forgedb restore` в **новый каталог**, проверяя логические ключи и именованные families.

## Изменение CLI, на которое нужно обратить внимание

До v1.0.0 обычный CLI `get` или `scan` мог открыть указанный ошибочно путь в режиме, разрешающем создание каталога базы. В v1.0.0 эти команды **никогда не создают отсутствующий каталог**: возвращают ошибку. Если у вас скрипт неявно создавал базу через GET/SCAN, измените его: используйте явную операцию `put` или `ColumnFamilies::open` с `create_if_missing=true`.

Новые команды `doctor`/`version` не ломают существующий FQL V1 и `cf` API. Команда `doctor` не выполняет repair и не удаляет неизвестные файлы.

## Экспорт и восстановление именованных families

- Логический archive V1 включает все **зарегистрированные действующие** families; физические папки ранее удалённых или неизвестных families не переносит.
- Сохраняются имена и бинарные пары key/value; numeric `ColumnFamilyId` при восстановлении могут поменяться (из-за отверстий в исходном реестре). После restore используйте `cf list` и не сохраняйте старые IDs в конфигурации приложения.
- Архив не сохраняет историю MVCC и tombstone, текущие WAL generation/sequence numbers, MANIFEST topology, пути внешних файлов или локальные ACL.
- Архив не шифруется и не подписывается. CRC32C обнаруживает типичные случайные повреждения, но не делает файл доверенным.
- Atomic mixed-family backup и mixed-family transactions не поддержаны (Issue #35).

## Откат

v1.0.0 не записывает новых версий физических WAL/SST/MANIFEST/CF_REGISTRY. Поэтому для данных, которые используют только эти форматы, предусмотрен безопасный путь: закрыть новую версию, сохранить отдельную offline-копию и заново открыть прежней версией **после проверки совместимости конкретной базы**. Откат бинарника не даёт автоматической возможности загрузить `.fdbk`: `LOGICAL_ARCHIVE V1` введён именно в v1.0.0.

Не редактируйте файлы базы вручную, не удаляйте orphan/unknown SST и не запускайте одновременно два процесса над одним каталогом. Перед реальным откатом используйте резервную копию, подготовленную до обновления, и тестовое восстановление в изолированном каталоге.

## Что осталось за границами

Нет общего FD process limit (#31), atomic mixed-family WAL/transactions (#35) и публикации этого crate под занятым именем на crates.io (#27). Подробно: `docs/GA_READINESS.md`, `docs/COMPATIBILITY.md`, `docs/RELEASE_POLICY.md`.
