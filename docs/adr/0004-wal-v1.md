# ADR 0004: один проверяемый кадр на WriteBatch в WAL V1

Статус: принято.

## Контекст

Первый durable write path должен восстанавливать атомарные batch, обнаруживать corruption и ограничивать память до
allocation. Fragmentation, block framing и resynchronization увеличивают пространство состояний recovery до появления
реальной необходимости в очень больших records.

## Решение

- Один `WriteBatch` кодируется одним логическим кадром.
- Файл и кадр имеют фиксированные versioned-заголовки.
- Заголовок файла и каждый полный кадр защищены CRC32C Castagnoli.
- Размер payload и operation count ограничиваются до allocation.
- Reader читает кадры строго последовательно и не ищет следующий magic после corruption.
- Только физически неполный последний кадр может быть отброшен.
- Unknown version и ненулевые reserved-поля отклоняются.

## Последствия

Положительные:

- атомарность batch естественно совпадает с границей кадра;
- простая и проверяемая recovery state machine;
- нет ложного восстановления после mid-file corruption;
- bounded memory очевидна из заголовка и `Limits`.

Отрицательные:

- один кадр не может превышать `max_batch_size` и `u32` layout limit;
- нет streaming очень больших batch;
- нет fragment reuse и block alignment;
- один повреждённый полный кадр блокирует все более поздние записи.

## Альтернативы

### Fragment records

Отложены до измеренной потребности. Они потребуют checksum и state machine для first/middle/last fragment,
а также доказательства атомарности при partial tail.

### Resynchronization по magic

Отклонена. Случайные bytes могут имитировать magic, а пропуск повреждённого batch создаёт sequence и state gaps,
которые не соответствуют подтверждённой истории.
