# ForgeDB v0.8.1 — SST Handle Cache & Reliability

Исправительный выпуск после v0.8.0. Цель — устранить постоянное удержание одного OS handle на каждый live SSTable при точечных чтениях без изменения формата хранения и правил удаления файлов.

## Реализовано

- Добавлен `TableHandlePool` — native SST point-read LRU pool, общий для поколений `VersionSet` и новых файлов, устанавливаемых через flush/compaction.
- `Options::table_cache_capacity` теперь действительно ограничивает **resident SST descriptors point-read pool** одного Database. По умолчанию 512, допустимо положительное значение.
- На открытии SST metadata (header/footer/index/Bloom/properties) валидируется как раньше, затем начальный FD закрывается; data blocks читаются lazy только при необходимости.
- При cache miss File открывается заново с проверкой size, DB identity, file number, sequence range и header checksum. Data block CRC32C, BlockHandle bounds и decoder checks сохранены.
- LRU eviction закрывает старый FD перед новым open; pool mutex обеспечивает последовательное чтение и строгую вместимость без временных превышений **внутри pool**.
- При reference-aware cleanup выселение pooled FD идёт до Windows `remove_file`. Неактивные объекты VersionSet не подменяются ссылкой на текущий manifest; объекты чтения продолжают удерживать защиту от premature deletion.
- Публичный `Database::table_handle_stats()` предоставляет capacity, open_handles, hits, misses, evictions, reopens; `Database::cache_stats()` для decoded blocks не меняется.

## Обновления тестов

- `point_read_budget_one_evicts_and_reopens_without_losing_values`: budget=1, несколько SST, LRU eviction/reopen, reopen всей базы.
- `pinned_scan_survives_compaction_and_retirement_evicts_windows_handles`: старый iterator удерживает SST, cleanup после release закрывает pooled handle и удаляет только доказанно retired files.
- `transaction_conflicts_and_snapshot_reads_survive_fd_eviction`: MVCC snapshots и optimistic write-write conflict detection после повторных открытий SST.
- `native_handle_cache_reopens_with_bounded_fd_and_rechecks_header`: повреждение header после eviction не превращается в успешный read; после восстановления valid file повторное чтение работает.
- Прежние suite WAL/recovery/compaction/FQL/CF остаются без изменения.

## Границы

`table_cache_capacity` **не является глобальным ограничением всех FD процесса**. В него не включаются scan cursors, компактация и временные файлы, WAL/MANIFEST/LOCK, а также sibling named Column Families (каждая имеет свой Database и свой pool). Это частичное выполнение общей задачи #31; она остаётся открытой.

Не реализованы смешанные атомарные операции между named Column Families (#35), глобальная FD eviction policy для streaming reads, новый WAL либо изменение persisted format. Релиз не утверждает снижения RSS или ускорения без отдельного измерения; глобальный mutex может сериализовать часть point lookup I/O.

## Совместимость

WAL V1, SSTable V1, MANIFEST reader V1+V2/writer V2, CURRENT V1, IDENTITY V1, CF_REGISTRY V1 без изменений; повторное открытие старых баз не требует миграции.
