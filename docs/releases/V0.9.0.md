# ForgeDB v0.9.0 — Performance Engine

Оптимизационное обновление встроенной key-value базы ForgeDB. Цель — убрать лишнюю работу внутри горячих SST/MVCC путей чтения и проверки транзакций, сохраняя корректность и возможность открыть старую базу.

## Реализовано

**SST handles:** вместо полного прохода всех resident File при LRU eviction используется ordered `BTreeSet<(access, file_number)>`. Выбор жертвы теперь O(log N) вместо O(N), поддержание индекса выполняется вместе с обновлением записи `BTreeMap` под тем же mutex. При удалении retired SST удаляются оба индекса. Ограничение `Options::table_cache_capacity` и существующий close-before-remove путь для Windows не меняются.

**MVCC scans:** проверка порядка source больше не копирует `TableEntry.value`; копируется `InternalKey`. При объединении нескольких sorted cursors значения версий, которые старше текущего snapshot либо скрыты уже выбранной версией ключа, пропускаются без клонирования. Порядок, tombstones, верхняя граница `limit` и snapshot visibility прежние.

**Optimistic transaction conflicts:** `latest_sequence_after` проходит перекрывающиеся L0 newest-first и пропускает устаревшие по sequence SST; в L1+ ищет возможный файл бинарным поиском по непересекающимся диапазонам, вместо перебора всех файлов уровня. Вычисление максимальной committed sequence остаётся прежним.

**Инициализация SCAN:** убран промежуточный `Vec<TableHandle>` с clone ссылок на все SST при каждом запуске. Streaming scan теперь обходит заимствованные `TableHandle` из текущего `VersionSet` и открывает курсоры только для overlapping SST. Сложность проверки диапазона пока O(N), но без лишнего массива из N элементов.

**Инструменты измерений:** добавлен `examples/performance_bench.rs`, выводит скорость/латентность p50/p95/p99 для холодных/прогретых GET, throughput и длительность полного SCAN и состояние cache handles. Benchmark выполняется в CI в коротком smoke-режиме Ubuntu/Windows (256 ключей, 1024 GET) и в полном Ubuntu workload (8192 ключей, 32768 GET), который обязательно должен вызвать eviction при capacity=8. Для сравнения версий используется параметризованный запуск. Изменение алгоритмической сложности само по себе не является обещанием ускорения на любой машине.

## Регрессионное покрытие

- `ordered_handle_lru_keeps_most_recent_file_and_maintains_exact_metrics`: capacity=2, три SST, повторное обращение к MRU, точное количество hits/misses/evictions/reopens.
- `conflict_validation_binary_search_finds_versions_in_leveled_sst`: сотни записей, manual compaction в L1+, актуальные point reads, stale transaction commit отвергается, повторное открытие подтверждает latest value.
- `mvcc_merge_discards_large_invisible_values_without_losing_snapshot_semantics`: 128-KiB values, 16 исторических версий, tombstones, old snapshot scan и latest scan.
- `narrow_range_scan_preserves_order_across_many_sst_without_handle_vector`: 48 SST, узкий half-open диапазон, отсутствие пропущенных или лишних ключей.
- Вся существующая матрица WAL/recovery/transactions, Windows cleanup, FQL и named Column Families остаётся обязательной.

## Ограничения

- Индекс LRU занимает O(N) дополнительной памяти и требует O(log N) операций на hit, потому изменения throughput требуется измерять отдельно.
- Shared mutex native File pool и полная metadata validation при первом cursor open не устранены; `table_cache_capacity` не является глобальным process FD лимитом, Issue #31 остаётся открытой.
- Результаты benchmark зависят от диска, ОС, FS cache, температуры, версии Rust, состояния CPU и конфигурации, не считаются SLA; сравнивать только похожие прогоны и указывать входные параметры.
- Глобальная mixed-family atomic WAL/MANIFEST (#35) не входит в версию.
- Persisted IDENTITY/WAL/SSTable/MANIFEST/CURRENT/CF_REGISTRY форматы без изменений, миграция не требуется.
