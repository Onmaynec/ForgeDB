# ForgeDB v0.7.0 — Column Families

## Новое API

`ColumnFamilies::open(path, Options)` открывает совместимый default DB и загружает отдельный verified registry. `list()`, `create(name)`, `drop_family(id)` управляют именованными families; методы `put/get/delete/write/scan/flush/compact_range/snapshot/begin_transaction` работают по `ColumnFamilyId`.

Пример:

```rust
use forgedb::{ColumnFamilies, ColumnFamilyId, Options, Result, WriteOptions};

fn demo() -> Result<()> {
    let families = ColumnFamilies::open("./data", Options::default())?;
    let users = families.create("users")?;
    families.put(users, b"42", b"Alice", WriteOptions::sync())?;
    assert_eq!(families.get(users, b"42")?, Some(b"Alice".to_vec()));
    assert_eq!(families.get(ColumnFamilyId::DEFAULT, b"42")?, None);
    families.close()
}
```

`list()` возвращает ID и имена для повторного открытия после restart. `create` с прежним именем после `drop_family` создаёт новый числовой ID; старые файлы не возвращаются в активный набор. Имена ограничены ASCII 1..=64 (`A-Za-z0-9_-`). Read-only не разрешает create/drop/put.

## Durability и failure policy

- Каждый named CF имеет отдельный durable WAL/LSM root; root single-family база остаётся неизменной.
- `CF_REGISTRY V1` содержит CRC32C, monotonic next ID, bounded record list и атомарную замену full snapshot с fsync.
- При создании CF сначала инициализируется и синхронизируется дочерняя база, затем публикуется registry.
- После аварии incomplete/unregistered catalog не удаляется и не присоединяется по догадке.
- Отсутствие зарегистрированной family или повреждённый registry — ошибка; silent recreation запрещена.
- При drop открытая family закрывается, registry публикуется без ID, каталог остаётся для диагностики.

## Ограничения первой реализации

- **Нет атомарных операций через две families**. `WriteBatch` и `Transaction` атомарны только в одном CF. Legacy `WriteBatch::put_cf` с ненулевым ID остаётся закрытым; используйте `ColumnFamilies::write(id, обычный batch)`.
- Нет общей временной шкалы MVCC, cross-family snapshots или serializable isolation.
- Каждая CF имеет собственные memtable, `block_cache_size` и readers; нет общей квоты RAM/FD.
- Drop оставляет orphan data и не является физической очисткой; ручное удаление каталогов без проверки ownership не рекомендуется.
- Фоновая compaction, restart-aware obsolete SST GC и unified CF MANIFEST остаются вне milestone.

## Persisted compatibility

Default WAL V1, SSTable V1, MANIFEST V2 writer/V1+V2 reader, CURRENT V1 и IDENTITY V1 не изменяются. Добавлен отдельный `CF_REGISTRY V1`, документирован в `docs/formats/CF_REGISTRY_V1.md`. Default API `Database::open` доступен как раньше.

## Проверки

Тесты: изоляция одноимённых ключей default/named CF, multiple flush/compaction/reopen, snapshot transaction isolation per CF, drop/recreate ID, registry checksum corruption, read-only и missing live CF, создание после orphan crash-directory. Release gate включает Linux/Windows stable и Rust 1.89, strict Clippy, fmt, workspace tests, doctests, release build и benchmark smoke.
